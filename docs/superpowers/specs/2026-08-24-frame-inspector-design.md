# Дизайн: разбор кадров и детальный вид

**Дата:** 2026-08-24
**Статус:** одобрен, готов к написанию плана реализации
**Основание:** схема `org.meshtastic:protobufs:2.7.26`, `com.squareup.wire:wire-runtime:6.4.5`
**Предыдущий этап:** `2026-08-22-ble-emulation-design.md` (эмулятор + BLE-транспорт)

## 1. Цель

Лента кадров сейчас показывает по одной строке на кадр и больше ничего. Кадр
приходит, мелькает и пропадает — посмотреть, что в нём было, нельзя. Этап
превращает ленту в инструмент разбора: кадр открывается и показывает своё
содержимое целиком, на языке схемы протокола.

## 2. Требования

Дословно, как поставлены:

1. Использовать 16-ричные идентификаторы нод.
2. Данные принятых кадров должны сохраняться.
3. Глубина хранения такая же, как сейчас у ленты кадров — 500 кадров.
4. В ленте кадров при щелчке по записи должен открываться детальный вид
   выбранного кадра.
5. Открывая детальный вид кадра, делать копию его данных и показывать их, чтобы
   вытеснение исходного кадра из ленты не влияло на открытый вид.
6. Пока открыт вид того или иного кадра, виды других кадров открыть нельзя.
7. Исследовать, какие типы кадров могут быть, и для каждого предусмотреть
   отображение специфической информации; выделить общую для всех кадров
   информацию и отображать её однотипно; отображать дату и время кадра по часам
   ноды.

Уточнено при обсуждении:

- Подписи полей — **только на английском**, именами из схемы протокола; единицы
  измерения — из комментариев схемы. Русский остаётся у рамки приложения
  (заголовки экранов, счётчики), но не у данных.
- «Сохраняться» означает: лента держит данные кадра целиком, а не строку
  описания, и держит их до вытеснения по глубине — чтобы кадр было чем открыть.
  Дискового хранилища не создаётся. Очистка ленты при подключении остаётся
  такой же, как сейчас: лента — снимок одного подключения.
- Разбор полный: все 19 вариантов `FromRadio` и все portnum.

## 3. Принятые решения

| Решение | Выбор | Обоснование |
| :--- | :--- | :--- |
| Хранение ленты | В памяти, без диска | Выбор заказчика. Подсистема хранения не появляется |
| Очистка при подключении | Сохраняется как сейчас | Решение заказчика. Лента остаётся снимком одного подключения, кадры разных устройств не смешиваются |
| Глубина | 500, как сейчас | Требование 3 |
| Подписи полей | Имена из схемы, английские | Требование заказчика. Снимает ~600 ручных переводов |
| Источник подписей | Аннотация `@WireField` во время выполнения | Retention = RUNTIME (проверено, `WireField.kt:25`); несёт `declaredName`, `tag`, `adapter`, `schemaIndex` |
| Полнота разбора | Обход полей + таблица подсказок | Полное покрытие без построчной ручной работы |
| Рефлексия | Java-рефлексия по `declaredFields` | `kotlin-reflect` — лишняя зависимость и вес; Java-рефлексии достаточно |
| Нагрузка `MeshPacket` | Таблица `PortNum` → способ чтения | Требование «все portnum»; для непротобуфных портов честный текст или hex |
| Детальный вид | Отдельный полноэкранный экран | Выбор заказчика. Требование 6 выполняется конструкцией |
| Снимок кадра | Хранение записи, а не индекса | Модели Wire неизменяемы; опасность — в позиции, а не в объекте (см. §9) |
| Время без метки ноды | Часы телефона с явной подписью | Выбор заказчика. Ничего не вычисляется и не выдаётся за чужое |

## 4. Глобальные ограничения

Значения — точные, менять нельзя:

- AGP 9.3.1, Gradle 9.7.1, Kotlin 2.4.10 (встроен в AGP 9), JDK 21.
- `compileSdk = 37`, `targetSdk = 36`, `minSdk = 26`. Compose BOM 2026.06.01.
- `org.meshtastic:protobufs:2.7.26`.
- **Новых зависимостей не добавляется.** В частности, `kotlin-reflect` под
  запретом: обход полей делается Java-рефлексией.
- Глубина ленты `PACKET_LOG_LIMIT = 500`.
- Формат идентификатора ноды: `!` + восемь строчных 16-ричных цифр.
- Подписи полей — английские, из схемы. Русский — только в рамке приложения.
- Разбор нагрузки не имеет права бросать исключение наружу.

## 5. Модель данных

Лента хранит запись, а не голый кадр:

```kotlin
data class FrameRecord(
    val seq: Long,              // номер внутри подключения, с единицы
    val receivedAtMillis: Long, // часы телефона, момент приёма
    val sourceAddress: String,  // "x00:11:22:.." либо "m:demo-1"
    val frame: FromRadio,
)
```

`sourceAddress` нужен не ленте — внутри одного подключения он у всех кадров
один и тот же, — а **снимку**. Открытый детальный вид переживает разрыв и
повторное подключение, которое ленту очищает; к этому моменту приложение может
быть подключено уже к другому устройству, и открытый кадр обязан сам говорить,
откуда он. Без этого поля снимок теряет происхождение ровно тогда, когда оно
становится неочевидным.

`seq` даёт кадру устойчивое имя. По нему кадр опознаётся в ленте и в открытом
виде даже после того, как соседи вытеснены. Первый кадр подключения получает
номер 1; счётчик сбрасывается вместе с лентой, при подключении. Сквозной
номер, продолжающий расти над пустой лентой, читался бы как ошибка: лента
пуста, а первый кадр в ней — `#1043`.

Модель отображения — без Compose, чтобы проверялась обычными JVM-тестами:

```kotlin
data class DetailField(val name: String, val value: String)
data class Section(val title: String, val fields: List<DetailField>)
data class FrameDetail(
    val title: String,
    val common: List<DetailField>,
    val sections: List<Section>,
)
```

Имя `DetailField`, а не `Field`: обходчик работает с `java.lang.reflect.Field`, и
два `Field` в одном файле — гарантированная путаница при чтении.

Список секций плоский. Вложенное сообщение не порождает вложенную секцию, а
даёт ещё одну секцию верхнего уровня, чей заголовок несёт путь:
`packet`, `packet.decoded`, `packet.decoded.payload (Position)`. Плоская модель
рисуется одним проходом и читается на узком экране без отступов, растущих
вправо.

## 6. Разбор

Четыре части. Каждая проверяется отдельно и не знает про Android.

### 6.1 FieldWalker

Обходит `declaredFields` сообщения Wire, читает на каждом аннотацию
`@WireField`, отдаёт поля в порядке `schemaIndex` как тройки «имя из схемы, тип
по схеме, значение».

- Имя поля: `declaredName`, если непустое, иначе имя свойства Kotlin. Это даёт
  ровно то имя, что стоит в `.proto` (`battery_level`, `rx_snr`, `hop_limit`).
- Поля со значением по умолчанию скрываются. Иначе `ModuleConfig` покажет 140
  нулей и утопит содержательное. На экране есть переключатель, возвращающий их.
- `unknownFields` при непустом значении показывается отдельной строкой. Это
  прямой признак, что прошивка ноды новее протобуфов приложения, — сведение,
  которое иначе негде увидеть.
- Вложенные сообщения обходятся рекурсивно и дают дополнительные секции
  верхнего уровня с путём в заголовке (см. §5), а не вложенные структуры.

Чтение значения идёт через `Field.setAccessible(true)`: Wire ставит аннотацию
на backing-поле (`@field:WireField`), а оно приватное.

### 6.2 FieldHints

Таблица на пару «сообщение, поле» → способ отображения значения. Здесь живёт
всё, чего обходчик знать не может, — порядка 80 записей вместо 600:

| Способ | Где применяется | Что делает |
| :--- | :--- | :--- |
| `NODE_ID` | `MeshPacket.from`, `.to`, `Data.dest`, `.source`, `MyNodeInfo.my_node_num`, `NodeInfo.num`, `NeighborInfo.node_id`, `Neighbor.node_id`, `RouteDiscovery.route[]` | `!a1b2c3d4`; `0xffffffff` дополняется пометкой широковещания; `0` — пометкой «не задан» |
| `NODE_ID_LAST_BYTE` | `MeshPacket.next_hop`, `.relay_node` | `0xab`. По схеме это **последний байт** номера ноды, а не номер |
| `EPOCH_SECONDS` | `MeshPacket.rx_time`, `NodeInfo.last_heard`, `Position.time`, `Telemetry.time`, `LogRecord.time` | Дата и время; нулевое значение — «не задано», а не 1970 год |
| `SCALED_1E7` | `Position.latitude_i`, `.longitude_i`, `MapReport.*_i`, `TAKPacketV2.*_i` | Градусы |
| `HEX_BYTES` | все поля типа `bytes` | Дамп с длиной |
| единица | `voltage` (V), `temperature` (°C), `battery_level` (%), `altitude` (m), `rx_snr` (dB), `rx_rssi` (dBm), прочие по комментариям схемы | Значение плюс единица |

Перечисления печатаются именем из схемы: у Wire `toString()` перечисления — это
его имя.

### 6.4 FrameDecoder

Собирает `FrameDetail`: определяет заполненный вариант `oneof` в `FromRadio`,
строит общую часть и передаёт содержимое обходчику. Для `MeshPacket`
дополнительно вызывает `PayloadCodecs`.

## 7. Общая часть кадра

Одинакова у всех девятнадцати вариантов:

| Строка | Источник |
| :--- | :--- |
| Номер в ленте | `FrameRecord.seq` |
| Тип кадра | имя заполненного поля `oneof`: `packet`, `my_info`, `config`, … |
| Размер | длина закодированного кадра |
| Часы ноды | `rx_time` / `last_heard` / `time`, если есть |
| Часы телефона | `FrameRecord.receivedAtMillis` |
| Источник | `FrameRecord.sourceAddress` |

Размер берётся повторным кодированием кадра: транспортный шов передаёт наверх
разобранный `FromRadio`, а не байты, и расширять шов ради одного числа — та же
ошибка, что разбиралась на прошлом этапе. Неизвестные поля Wire сохраняет и
кодирует обратно, поэтому длина совпадает с принятой.

Метки времени подписаны раздельно и никогда не подставляются одна вместо
другой. У шестнадцати вариантов из девятнадцати метки ноды нет вовсе — там
стоит только строка часов телефона.

## 8. Лента

- Тип `packetLog` меняется на `List<FrameRecord>`.
- Очистка ленты при подключении остаётся: строка `_packetLog.value = emptyList()`
  в `connect` не трогается. Вместе с лентой обнуляется счётчик `seq`.
- Метка времени и адрес источника проставляются в `onDataReceived`. Часы берутся
  из уже имеющегося параметра `now: () -> Long`, так что тесты идут на
  виртуальных часах.
- Глубина 500 сохраняется.

**Счётчик принятого.** Сейчас на экране «Принято кадров: N», где N — размер
ленты, и это число молча упирается в 500: после вытеснения оно перестаёт расти,
хотя приём продолжается. На коротких приёмках потолок не достигался, поэтому
дефект незаметен, — но это именно дефект, а не задумка. Раз `seq` всё равно
появляется, честное число достаётся даром: показываются два, «принято за
подключение» и «в ленте».

Это выходит за семь поставленных пунктов. Стоит одной строки на экране и
никакой отдельной работы; если считаете лишним — убирается вычёркиванием этого
абзаца.

Строка ленты:

```
#1042  14:23:09  MeshPacket  !a1b2c3d4 → !ffffffff  TELEMETRY_APP
```

Время в строке — часы телефона: они есть у каждого кадра, и лента остаётся
однородной. Часы ноды показываются в детальном виде.

## 9. Экран кадра

Строка ленты становится нажимаемой. Выбор живёт в единственном состоянии
`FrameRecord?` в `MainActivity`: не null — показывается `FrameDetailScreen`,
null — лента.

**Требование 6** выполняется конструкцией: лента во время просмотра не видна,
нажимать не по чему, а состояние по определению хранит один кадр. Отдельного
запрета не пишется — пишется тест, фиксирующий, что состояние одиночное.

**Требование 5** выполняется хранением записи, а не позиции. Модели Wire —
неизменяемые data-классы; держать ссылку и делать глубокую копию наблюдаемо
одно и то же, изменить объект невозможно. Опасность, от которой требование
защищает, при этом настоящая, но она в другом месте: если хранить **индекс** в
списке, после вытеснения тот же индекс укажет на другой кадр и открытый вид
молча подменится, а после очистки ленты при подключении не укажет ни на что.
Поэтому хранится запись, и пишутся тесты ровно на эти два сценария.

Два следствия из состояния проекта:

- Ориентация в манифесте не зафиксирована, поэтому выбор кладётся в
  `rememberSaveable` с сохранением через `FromRadio.ADAPTER.encode()`. Иначе
  поворот телефона закроет открытый кадр.
- `BackHandler` в проекте отсутствует. Он нужен экрану кадра, иначе аппаратная
  «Назад» выйдет из приложения вместо возврата в ленту. Тем же добавляется и
  ленте — сейчас она страдает тем же, и это одна строка в той же работе.

На экране есть переключатель «показать все поля», возвращающий скрытые
умолчания.

## 10. Отказы

Разбор нагрузки обязан быть невозмутимым. `ProtoAdapter.decode` бросает на
мусоре, а мусор будет: обрезанный пакет, чужой формат под знакомым portnum,
нагрузка от прошивки новее протобуфов. Каждый разбор нагрузки обёрнут, и при
отказе секция показывает причину и hex — но не роняет экран и не прячет кадр.

Зашифрованные `MeshPacket` (`encrypted` заполнено, `decoded` пусто) — не отказ,
а нормальное состояние: содержимое недоступно без ключей канала. Показывается
факт шифрования, размер и hex.

## 11. Тестирование

Обычные JVM-тесты, как весь существующий набор.

- `FieldWalker`: чтение значения рефлексией работает; порядок по `schemaIndex`;
  умолчания скрыты и возвращаются флагом; `unknownFields` видны; вложенные
  сообщения дают вложенные секции.
- `FieldHints`: идентификатор ноды, широковещательный адрес, нулевой адрес,
  `next_hop` как байт, эпоха в дату при фиксированном часовом поясе, нулевая
  эпоха как «не задано», масштаб координат, единицы.
- `PayloadCodecs`: по представителю на каждую группу портов; неизвестный
  portnum; **битая нагрузка не бросает, а даёт секцию с причиной и hex**.
- `FrameDecoder`: табличный тест по всем 19 вариантам `FromRadio` — у каждого
  есть заголовок и полная общая часть. Тест умеет падать при росте схемы, и в
  этом его смысл: он не даст забыть вариант.
- Лента: очищается при подключении, и `seq` обнуляется вместе с ней; режется на
  500; `seq` монотонен внутри подключения; счётчик принятого за подключение
  продолжает расти после того, как лента упёрлась в 500.
- Снимок, вытеснение: открыть кадр, дописать 500 новых, убедиться, что данные
  открытого не изменились.
- Снимок, очистка: открыть кадр, выполнить подключение (лента очищается,
  `seq` обнуляется), убедиться, что открытый кадр цел и по-прежнему называет
  свой источник.

отказ от очистки, счётчик принятого), `ui/PacketLogScreen.kt` (нажатие, два
счётчика, `BackHandler`), `MainActivity.kt` (состояние выбора, `BackHandler`).

Удаляется: `ui/PacketFormatter.kt` — его работу забирает `FrameSummary`.

Крупных файлов не возникает: два самых больших, `FieldHints` и `PayloadCodecs`,
— плоские таблицы.

## 13. Риски

**Чтение приватных полей рефлексией.** Доступность аннотации проверена по
исходникам, само чтение значения — нет. Это первая задача плана, с настоящим
тестом, а не проверка в конце. Запасной путь, если не заработает, — публичные
геттеры Kotlin-свойств (`getBattery_level()`), они существуют всегда; цена —
сопоставление геттера с аннотированным полем по имени.

**Обфускация.** Обход держится на именах полей и аннотациях. Сейчас
`isMinifyEnabled = false`, поэтому работы нет, но при включении `minify`
понадобятся keep-правила на `org.meshtastic.proto.**`, иначе детальный вид
покажет `a`, `b`, `c` вместо имён.

**Открытый кадр переживает очистку ленты.** Лента стирается при подключении, а
детальный вид в этот момент может быть открыт. Кадр обязан остаться на экране
целым: он уже не принадлежит ленте. Это не риск реализации, а сценарий, который
легко упустить, поэтому он вынесен в тесты отдельной строкой.

## 14. Что остаётся вне этапа

- Дисковое хранение и история между запусками.
- Поиск и фильтрация по ленте.
- Расшифровка `MeshPacket` по ключам канала.
- Распаковка Unishox2 и zstd.
- Отправка кадров — этап только про приём.
